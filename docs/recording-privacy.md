# Private recording administration / Quyền riêng tư khi vận hành

VI: Admin và ContentEditor vẫn quản lý audio bài học. Danh sách CMS chỉ hiện bản thu cá nhân thuộc chính tài khoản đang đăng nhập. Quyền vận hành không tự cấp quyền xem tên/nguồn bản thu, xem job hoặc retry xử lý bản thu riêng của người khác.

`GET /api/v1/admin/media` filters to lesson_audio or the current owner **before** ordering and the50-row limit. `GET /api/v1/admin/jobs` applies the same ownership rule through the referenced media asset before its50-row limit; orphan jobs are omitted from this media operations view. Stable ID tie-breakers supplement the existing newest-first ordering. Neither metadata route resolves blob storage or issues a playback/upload grant.

`POST /api/v1/admin/jobs/{id}/retry` still requires Admin and CSRF. It resolves only a currently authorized media owner before receipt lookup, resource locking, audit writes or generation changes. A known foreign recording job and an unknown job both return404 `job_not_found`. Existing authorized editorial-audio and own-recording retries retain the same payload-bound, exactly-once receipt behavior and quota-owner lock. This does not add a learner retry endpoint or recording-sharing feature. The existing owner-only library, playback and deletion rules continue to apply.

Five relational cases cover Admin and Editor catalog isolation, own/editorial inclusion, metadata/key nondisclosure, role/anonymous boundaries, private-job filtering, known/unknown404 with unchanged generations/rowversions/jobs/receipts/audits, authorized replay and CSRF. An initial test redundantly called the older MediaService-backed detail/playback endpoints in a fixture with no storage configuration; it received503 from that dependency's construction. Those unrelated assertions were removed from this storage-free catalog/retry suite. Actual playback ACLs remain covered by the real Storage suite. No schema migration, blob operation, native browser input or learner-progress backfill is needed for the fix.
