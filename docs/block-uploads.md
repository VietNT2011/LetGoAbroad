# Audio block uploads / Tiếp tục gửi audio

VI: CMS gửi audio thành từng block4 MiB. Khi mạng lỗi hoặc người dùng tạm dừng, nút gửi lại tiếp tục ở block chưa nhận ACK, với cùng file/ID/phiên gửi. Đã gửi100% byte không có nghĩa media Ready: commit danh sách block và complete vẫn phải thành công; worker tiếp tục xác minh/transcode.

The browser retains an immutable File, create-command ID, staging grant, acknowledged block index and commit/completion state **in memory only**. Fixed-length Base64 IDs are unique per task and URL-encoded; an ordered Latest block list permits an unknown commit response to be retried using committed or uncommitted blocks. A lost block ACK resends the same block identity/bytes. After a successful commit ACK, a lost Complete ACK retries only Complete, avoiding a staging ETag rewrite after the server may have pinned it. Accepted Complete is still a queued acknowledgment, never an asserted Ready state.

Pause aborts the current request but retains the task; a late response is checked against the abort signal before progressing. The task pins actor/epoch through raw SAS requests and stops during identity verification or changes. API commands use the existing actor-bound CSRF transport. Blob fetches omit cookies/referrers; SAS URLs are not logged or persisted. Unmount aborts active transfer. Server quota/expiry, ETag freeze, decode validation, job fencing and playback ACLs remain authoritative and unchanged.

Files/source fields stay fixed while a task exists. Explicitly abandoning a task does not delete server data and warns that an unknown Complete may already have queued processing; the asset list can be refreshed before starting another upload. Closing/reloading the tab loses resume state. Grants retain the existing15-minute server expiry; a new reservation is not silently created when the old grant expires. Durable cross-reload resume/grant renewal remains separate work.

Thirteen frontend transport cases cover ordered chunks, HTTP/lost-ACK retries, commit/Complete boundaries, actor changes/verification, cancellation/late responses, invalid file bounds, confirmed replay, concurrent sends, expiry and codec MIME normalization. One real SQL/Azurite/FFmpeg case stages/retries blocks, commits twice before Complete, repeats Complete, verifies Ready and one processing job, and rejects Admin playback of another learner's private recording. The fixture is a synthetic technical tone, not an authored listening lesson. Full previous local backend suites remain applicable to unchanged application C# source; current-head CI reruns all profiles, including the added Storage case. Native browser/mobile networking acceptance is not claimed.

Protocol references: [Microsoft Put Block](https://learn.microsoft.com/en-us/rest/api/storageservices/put-block), [Microsoft Put Block List](https://learn.microsoft.com/en-us/rest/api/storageservices/put-block-list).
